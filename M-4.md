## Step 1 — mai-project-mcp: Typed Resolve Endpoints

Add 3 new routes to `mai-project-mcp/src/routes/tasks.ts`, following the same pattern as the `/block/*` endpoints.

### POST /tasks/:id/resolve/decision

```
body: { choice: string }
```

1. Validate task exists and is `BLOCKED` with `blocker_type = 'DECISION'`
2. Merge `{ choice }` into existing `blocker_payload` (alongside original `question` / `options`)
3. Set `status: 'OPEN'`, clear `assigned_agent`, set `blocker_resolved_at: now`, update `updated_at`
4. Call `publishStateChange(redis, id, { task_id, from: 'BLOCKED', to: 'OPEN', blocker_type: 'DECISION', choice, timestamp })`

### POST /tasks/:id/resolve/clarification

```
body: { response: string }
```

1. Validate task exists and is `BLOCKED` with `blocker_type = 'CLARIFICATION'`
2. Append `"\n\nClarification: {response}"` to `task.description` (agent sees it on re-claim)
3. Merge `{ response }` into `blocker_payload`
4. Set `status: 'OPEN'`, clear `assigned_agent`, set `blocker_resolved_at: now`
5. Publish state change event

### POST /tasks/:id/resolve/risk

```
body: { approved: boolean, notes?: string }
```

1. Validate task exists and is `BLOCKED` with `blocker_type = 'RISK'`
2. If `approved: true`: set `status: 'OPEN'`, clear `assigned_agent`, set `blocker_resolved_at: now`
   - If original `severity === 'critical'`: unblock sibling `IN_PROGRESS` tasks that were mass-blocked by the same critical risk — set their `status: 'OPEN'`, clear `blocker_type`, clear `blocker_payload`
3. If `approved: false`: set `status: 'DONE'`, set `blocker_resolved_at: now` (task is killed)
4. Merge `{ approved, notes }` into `blocker_payload`
5. Publish state change event with `{ approved }`

### server/ws-relay.ts

- Open a **dedicated** Redis `createClient` connection for subscriptions (Redis requires a separate connection for pub/sub vs commands)
- `PSUBSCRIBE task.* project.*` — catches all task state changes and file-changed events from mai-watcher
- Maintain `Set<WebSocket>` of connected clients
- On Redis pattern message: broadcast `JSON.stringify({ channel, payload: JSON.parse(message) })` to all clients
- Export `addClient(ws: WebSocket)` and `removeClient(ws: WebSocket)` for the WebSocket route handler
- Export `initRelay()` async function that connects the subscriber; called on server startup

### server/routes/api.ts

All upstream calls use env vars: `REGISTRY_URL`, `PROJECT_MCP_URL`, `DISPATCHER_URL`.

```
GET /api/overview
```
- Fetch `REGISTRY_URL/projects` → list of projects
- For each: `PROJECT_MCP_URL/projects/:id/tasks` → count by status
- Return `Array<{ id, name, open, inProgress, blocked, done, escalations }>`

```
GET /api/escalations
```
- Same fetch pipeline; filter tasks to `status === 'BLOCKED'` and `blocker_type IN ['DECISION','CLARIFICATION','RISK']`
- Parse `blocker_payload` JSON for each
- Return flat array with `project_id`, `project_name` included

```
GET /api/agents
```
- `DISPATCHER_URL/agents` → agent profile list
- For each: `DISPATCHER_URL/agents/:id/budget` → budget status
- Return merged array

```
POST /api/tasks/:taskId/resolve/decision
POST /api/tasks/:taskId/resolve/clarification
POST /api/tasks/:taskId/resolve/risk
```
Proxy routes: forward body to `PROJECT_MCP_URL/tasks/:taskId/resolve/{type}`. Return upstream response. These exist to avoid CORS in the browser.

```
GET /api/projects/:id/tasks
```
Proxy: forward to `PROJECT_MCP_URL/projects/:id/tasks`.

### src/ws.ts — WebSocket singleton

- Connects to `ws://${window.location.host}/ws`
- Reconnects on close/error with exponential backoff: 1 s, 2 s, 4 s, … capped at 30 s
- `subscribe(handler: (event: WsEvent) => void): () => void` — returns unsubscribe function
- `useWsEvents(handler)` React hook — calls `subscribe` in `useEffect`, auto-unsubscribes on unmount

```typescript
interface WsEvent {
  channel: string;    // e.g. "task.{id}.state_changed"
  payload: Record<string, unknown>;
}
```

### src/pages/Overview.tsx

### src/pages/ProjectKanban.tsx

- URL param: `projectId`
- `fetchProjectTasks(projectId)` on mount; group by `status` into 4 columns
- `useWsEvents`: filter events matching this `project_id`, update or add/remove task cards
- Columns: `OPEN` | `IN_PROGRESS` | `BLOCKED` | `DONE`
- `<TaskCard>` shows: title, priority, `assigned_agent`, `<BlockerBadge>` if BLOCKED

### src/pages/EscalationQueue.tsx

- `fetchEscalations()` on mount
- `useWsEvents`: append new escalation items on `to: 'BLOCKED'` events with human-required blocker types; remove on `from: 'BLOCKED'` events
- Sort: RISK critical → RISK high → RISK others → DECISION → CLARIFICATION; secondary by `created_at` asc
- Render `<EscalationForm>` per item

### src/components/EscalationForm.tsx

- **DECISION**: renders `payload.question` + one button per option in `payload.options`; on click → `resolveDecision(taskId, choice)` → optimistically remove from list
- **CLARIFICATION**: renders `payload.question` + `<textarea>` + Submit button; on submit → `resolveClarification(taskId, response)` → optimistically remove
- **RISK**: renders `payload.description` + `<BlockerBadge severity={payload.severity}>` + optional notes `<textarea>` + Approve / Reject buttons; on click → `resolveRisk(taskId, approved, notes)` → optimistically remove

## Risks

### RISK 1 — WebSocket events missed on dashboard restart (LOW)
Redis pub/sub delivers only to live subscribers. If the dashboard restarts, events during downtime are lost. On reconnect, the client re-fetches `/api/escalations` and `/api/overview` to restore full state from REST. No event replay mechanism is needed.

### RISK 2 — Agent re-claims resolved task without resolution context (MEDIUM)
Fixed by Step 2 (manifest injection). Both `mai-project-mcp` and `mai-dispatcher` must be rebuilt together; rebuilding only one will leave the loop incomplete.

### RISK 3 — Sibling task state after critical RISK rejection (LOW)
When a critical RISK is **rejected**, sibling tasks that were mass-blocked remain BLOCKED. The operator must manually close or reset them. M5 can add a bulk-close endpoint.

### RISK 4 — Vite dev server CORS / proxy (LOW)
Dev mode runs Vite on a different port than Fastify. The `vite.config.ts` proxy config handles `/api` and `/ws` forwarding. This is dev-only; the production Docker image serves everything from the same Fastify port.

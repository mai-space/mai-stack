# M2 — Intelligence Layer

> Add context awareness: file change detection, persistent agent memory, and full Context Manifest assembly. After M2, every claimed task arrives with project instructions, relevant code, and relevant past decisions pre-assembled. Agents never receive bare task descriptions.

---

## Scope

M2 adds three new services. M1 services (mai-registry, mai-project-mcp, mai-code-mcp) receive minor REST additions to support the dispatcher.

| Service | Type | Port (internal) | Host-exposed |
|---|---|---|---|
| mai-watcher | New | — | No |
| mai-memory-mcp | New | 3458 | No |
| mai-dispatcher | New | 3460 | **Yes** |

After M2, local tools (Cursor, Claude Code, opencode) connect to the dispatcher at `:3460`. The dispatcher is the only externally exposed MCP endpoint. mai-project-mcp remains internal.

## Step 1 — mai-watcher

**Purpose:** Watch all project workspaces for file changes. Debounce and set Redis dirty flags. Publish file-changed events. Does not trigger reindex — that is the dispatcher's decision.

### Dependencies

```json
{
  "dependencies": {
    "chokidar": "^3.6.0",
    "redis": "^4.7.0"
  }
}
```

No Fastify — mai-watcher has no HTTP API. It is a pure worker process.

### Redis Keys

| Key | Type | Value | Written by | Read by |
|---|---|---|---|---|
| `project:{id}:dirty` | string | `"1"` / `"0"` | mai-watcher | mai-dispatcher |
| `project:{id}:last_changed_at` | string | epoch_ms | mai-watcher | mai-dispatcher |

Published channels:

| Channel | Payload |
|---|---|
| `project:{id}:files_changed` | `{ project_id, timestamp_ms, paths_sample }` |

### Startup Sequence

```
1. Validate REDIS_URL present; exit(1) if absent
2. Connect Redis client
3. syncProjects() — fetch all projects from REGISTRY_URL (retry pattern)
4. setInterval(syncProjects, RESYNC_INTERVAL_MS) — re-sync every 60s for new projects
5. SIGTERM → stop all watchers, disconnect Redis
```

### Watcher Logic

Key decisions:
- `ignoreInitial: true` — do not fire on startup tree scan (would dirty-flag everything)
- `awaitWriteFinish` — de-bounce partial writes from editors
- Per-project debounce timers; paths accumulate within window, flushed together
- `USE_POLLING` env var for macOS/NFS environments where inotify doesn't propagate

### Environment Variables

```
REDIS_URL=redis://redis:6379
REGISTRY_URL=http://mai-registry:3459
DEBOUNCE_MS=5000
RESYNC_INTERVAL_MS=60000
USE_POLLING=false           # set true on macOS hosts
POLLING_INTERVAL_MS=2000
```

## Step 2 — mai-memory-mcp

**Purpose:** Per-project persistent key-value memory. Agents write during tasks; dispatcher reads during manifest assembly.

### Dependencies

```json
{
  "dependencies": {
    "fastify": "^4.28.1",
    "@fastify/cors": "^9.0.1",
    "redis": "^4.7.0",
    "@modelcontextprotocol/sdk": "^1.12.0",
    "zod": "^3.23.8"
  }
}
```

### Redis Data Model

Three structures per project for O(1) upsert-by-key:

```
memory:{projectId}:{id}     Hash   id, project_id, key, value, created_at, updated_at
memory:{projectId}:index    ZSet   member=id, score=epoch_ms     (ordered listing)
memory:{projectId}:key-index  Hash   field=key, value=id          (upsert dedup)
```

**Upsert-by-key:** `HGET memory:{projectId}:key-index {key}` — if found, update the existing entry; if not, create new and register in both index structures.

### REST API

| Method | Path | Notes |
|---|---|---|
| `GET` | `/health` | `{ status, service, uptime }` |
| `GET` | `/projects/:projectId/memories` | List all; `?limit=50` |
| `POST` | `/projects/:projectId/memories` | Body: `{ key, value }` — upserts by key; 201 |
| `GET` | `/projects/:projectId/memories/recall` | `?q=query&limit=10` — keyword match |
| `DELETE` | `/projects/:projectId/memories/:key` | Delete by key; 204; 404 if not found |

### MCP Tools

**`remember`** — upserts memory entry by key  
**`recall`** — keyword search on key + value; returns top N by score desc  
**`forget`** — deletes memory entry by key  
**`list_memories`** — returns most recent N entries

## Step 3 — mai-dispatcher

**Purpose:** The public MCP gateway. Intercepts `claim_task` to run a pre-task freshness check and assemble a full Context Manifest. Proxies all other MCP tools to mai-project-mcp or mai-memory-mcp.

### Dependencies

```json
{
  "dependencies": {
    "fastify": "^4.28.1",
    "@fastify/cors": "^9.0.1",
    "redis": "^4.7.0",
    "@modelcontextprotocol/sdk": "^1.12.0",
    "js-yaml": "^4.1.0",
    "zod": "^3.23.8"
  }
}
```

### Environment Variables

```
PORT=3460
REDIS_URL=redis://redis:6379
REGISTRY_URL=http://mai-registry:3459
PROJECT_MCP_URL=http://mai-project-mcp:3456
CODE_MCP_URL=http://mai-code-mcp:3457
MEMORY_MCP_URL=http://mai-memory-mcp:3458
CONFIG_PATH=/config/agents.yml
REINDEX_TIMEOUT_MS=30000
```

### Pre-task Freshness Check

```
1. GET project:{id}:dirty from Redis → if not "1": skip
2. Fetch project from registry → get last_indexed_at + reindex_threshold_minutes
3. IF (now - last_indexed_at) <= threshold: clear dirty flag, skip
4. POST /reindex/:id to mai-code-mcp → start reindex
5. Poll GET /reindex/:id/status every 1s until done/error/timeout
6. On success: SET project:{id}:dirty "0"
7. On timeout: include stale warning in manifest; leave dirty="1" for next attempt
```

### Context Manifest Assembly

Fetched in parallel via `Promise.allSettled` (failures degrade section gracefully):

- **PROJECT CONTEXT** — registry `system_prompt_override` + AGENTS.md content
- **RELEVANT CODE** — top 5 chunks from `POST /search/:projectId` on mai-code-mcp
- **PROJECT STATE** — task counts + recent completions from mai-project-mcp
- **TASK DEPENDENCIES** — parent/child tasks from mai-project-mcp
- **MEMORY RECALL** — recent memories from mai-memory-mcp
- **IF YOU CANNOT PROCEED** — static blocker tool instructions
- **YOUR TASK** — task description + priority + lease TTL

### MCP Tools

| Tool | Behaviour |
|---|---|
| `claim_task` | **Intercepted** — freshness check + manifest assembly before returning task |
| `complete_task` | Proxy → `POST /tasks/:id/complete` |
| `renew_lease` | Proxy → `POST /tasks/:id/renew-lease` |
| `create_subtask` | Proxy → `POST /tasks/:id/subtask` |
| `request_decision` | Proxy → `POST /tasks/:id/block/decision` |
| `request_clarification` | Proxy → `POST /tasks/:id/block/clarification` |
| `flag_risk` | Proxy → `POST /tasks/:id/block/risk` |
| `reassign_task` | Proxy → `POST /tasks/:id/reassign` |
| `remember` | Proxy → `POST /projects/:id/memories` |
| `recall` | Proxy → `GET /projects/:id/memories/recall?q=...` |
| `forget` | Proxy → `DELETE /projects/:id/memories/:key` |
| `list_memories` | Proxy → `GET /projects/:id/memories` |

`claim_task` uses a retry loop: `GET /projects/:id/tasks` → sort OPEN by priority → `POST /tasks/:id/claim` → on 409 (race) try next task.

```bash

docker compose up -d

mkdir -p ${WORKSPACES_PATH}/app-a

# → "1"

# 4. Create a task
docker compose exec mai-project-mcp \
  curl -s -X POST http://localhost:3456/projects/app-a/tasks \

docker compose exec mai-memory-mcp \

# Expect: { "status": "ok", "service": "mai-dispatcher" }

# Full MCP test: connect an SSE client to localhost:3460 and call claim_task
```

## Risks

### RISK 1 — Chokidar on Docker Bind Mounts (HIGH on macOS)

inotify events don't propagate from host into container on macOS/NFS. Set `WATCHER_USE_POLLING=true` in `.env` for macOS development. On Linux production hosts, default (`false`) works correctly.

### RISK 2 — Reindex Timeout During claim_task (MEDIUM)

A large codebase may take longer than `REINDEX_TIMEOUT_MS` (30s). On timeout, the dispatcher includes a stale warning in the RELEVANT CODE section and leaves `dirty="1"` for the next claim attempt. `REINDEX_TIMEOUT_MS` is configurable.

### RISK 3 — AGENTS.md File Access (MEDIUM)

`agents_md_path` from the registry must be a container-side path (`/workspaces/app-a/AGENTS.md`). The dispatcher mounts `WORKSPACES_PATH:/workspaces:ro`. If the file is absent, the manifest degrades gracefully (PROJECT CONTEXT section shows only `system_prompt_override`).

### RISK 4 — claim_task TOCTOU Race (MEDIUM)

Two agents selecting the same task simultaneously: `GET /projects/:id/tasks` → select OPEN → `POST /tasks/:id/claim` → 409. The `claimNextTask` retry loop handles this: on 409, try the next task in priority order. No double-claim is possible because mai-project-mcp's `/claim` checks `status === 'OPEN'` atomically before updating.

### RISK 5 — Project ID Consistency (LOW)

The registry uses slug IDs (e.g., `app-a`). mai-project-mcp uses UUID by default. The dispatcher calls both services with the same project ID. Enforce by always creating mai-project-mcp projects with an explicit `id` matching the registry slug. `POST /projects` in mai-project-mcp now accepts an optional `id` field for this purpose.

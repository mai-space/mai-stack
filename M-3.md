# M3 — Governance

> Add per-agent budget ledgers, rate limiting, concurrency tracking, and a state machine to the dispatcher. After M3, every `claim_task` call is validated against agent policy. Over-budget agents are gracefully shut down. All governance state lives in Redis and auto-expires at midnight.

---

M3 touches exactly three files inside `mai-dispatcher`. No other services change. No new npm dependencies. No docker-compose changes.

## Redis Key Schema

| Key | Type | Value | TTL | Written by | Read by |
|---|---|---|---|---|---|
| `budget:{agentId}:{YYYY-MM-DD}` | string (float) | USD spent today | 48 h | governance.ts | governance.ts |
| `budget:{provider}:{YYYY-MM-DD}` | string (float) | Provider-level spend (informational) | 48 h | governance.ts | budget endpoint |
| `agent:{agentId}:state` | string (enum) | Budget state machine value | 48 h | governance.ts | governance.ts |
| `agent:{agentId}:active_tasks` | string (int) | Current concurrent task count | None | governance.ts | governance.ts |
| `ratelimit:{agentId}:{YYYY-MM-DDTHH:MM}` | string (int) | Requests this minute | 120 s | governance.ts | governance.ts |

**48 h TTL on budget + state keys = automatic midnight reset with no cron job required.**

## Budget State Machine

```
IDLE ──[claim: budget ok + rate ok + concurrency ok]──▶ WORKING
WORKING ──[task completes]──▶ IDLE
WORKING ──[budget ≥ 90% on next claim]──▶ GRACEFUL_SHUTDOWN
  └─▶ finish current task, reject all new claim_task calls
WORKING ──[budget ≥ 100% on next claim]──▶ HARD_PAUSE (immediate)
  └─▶ reject all new claim_task calls until Redis key expires
GRACEFUL_SHUTDOWN / HARD_PAUSE ──[midnight: Redis TTL expires]──▶ IDLE (implicit)
```

## Step 1 — governance.ts

New module. Owns all Redis key names and TTLs. Exports pure async functions — no singletons, no global state beyond Redis.

### Exported Functions

**`checkGovernance(redis, agentId, profile, allowedAgentIds)`** → `GovernanceResult`

Runs four ordered checks. Any failure returns immediately:

1. **Allowed agents** — if `allowedAgentIds.length > 0` and agent not in list → `agent_not_allowed`
2. **State gate** — if state is `GRACEFUL_SHUTDOWN` → `graceful_shutdown`; if `HARD_PAUSE` → `budget_exhausted`
3. **Rate limit** — fixed-window per minute via `INCR` + `EXPIRE 120`; if `count > requests_per_minute` → `rate_limited` + `retry_after: 60`
4. **Concurrency** — if `active_tasks >= max_concurrent_tasks` → `concurrency_limit`
5. **Budget threshold** — if `spent / daily_usd >= 1.0` → write `HARD_PAUSE` state, return `budget_exhausted`; if `>= 0.9` → write `GRACEFUL_SHUTDOWN`, return `graceful_shutdown`

Budget check is last: rate and concurrency are cheap reads; budget requires an extra key read and may trigger state writes.

**`recordClaim(redis, agentId, profile)`**

Called only after a task is successfully claimed from mai-project-mcp (not before). Charges `per_task_usd` upfront to both agent and provider budget keys. Increments `active_tasks`. Transitions state `IDLE → WORKING`.

**`recordComplete(redis, agentId)`**

Called from `complete_task`. Decrements `active_tasks` (floor 0). Transitions `WORKING → IDLE` if not in `GRACEFUL_SHUTDOWN` / `HARD_PAUSE` (those persist until key expiry).

**`getBudgetStatus(redis, profile)`** → `BudgetStatus`

Reads all four keys for an agent. Returns `{ agent_id, state, daily_usd, spent_usd, pct, active_tasks, provider, provider_spent_usd }`.

### TTL Strategy

Budget and state keys get 48 h TTL on first write (detected via `EXISTS` before `INCRBYFLOAT`). This ensures the key expires by end of next calendar day regardless of when it was first written. Two concurrent "first write" races both execute `EXPIRE 172800` — idempotent and harmless.

## Step 2 — task-tools.ts Modifications

### claim_task — new call sequence

```
1. Resolve profile: getAgentProfiles().find(p => p.id === agent_id)
   → if not found: return { task: null, reason: 'unknown_agent' }

2. Fetch project allowed_agent_ids from registry
   → GET REGISTRY_URL/projects/:project_id → parse allowed_agent_ids[]

3. checkGovernance(redis, agent_id, profile, allowedAgentIds)
   → if !allowed: return { task: null, reason, retry_after? }

4. checkFreshness(...)              [unchanged from M2]

5. claimNextTask(project_id, agent_id)   [unchanged from M2]
   → if !task: return { task: null, reason: 'no_tasks_available' }

6. recordClaim(redis, agent_id, profile)   ← NEW (only after successful claim)

7. assembleManifest(...)            [unchanged from M2]
   → return { task, context_manifest, lease_expires_at }
```

Governance runs **before** freshness check (no point reindexing for a rejected agent). `recordClaim` runs **after** successful claim (never charge budget for a race-lost or empty-queue claim).

### complete_task — extended signature

```typescript
{
  task_id: z.string(),
  agent_id: z.string().optional(),    // added; used to update concurrency state
  cost_usd: z.number().optional(),    // actual spend; adjusts per_task_usd estimate
}
```

If `agent_id` is provided and profile is found: apply `cost_usd` delta to budget keys (if provided), then call `recordComplete`. If `agent_id` is absent, proxy completes normally with no governance state update (backwards-compatible).

## Risks

### RISK 1 — active_tasks Leaks on Crash (MEDIUM)
If the dispatcher crashes after `recordClaim` (which increments concurrency) but before `recordComplete` (which decrements), the counter stays elevated permanently. The agent becomes stuck at its concurrency limit.

**Mitigation:** No TTL on `active_tasks` — crashes require explicit operator reset (`redis-cli set agent:{id}:active_tasks 0`). M5 will add a startup reconciliation that cross-references live task count in mai-project-mcp.

### RISK 2 — complete_task Missing agent_id from Existing Callers (MEDIUM)
`agent_id` is optional for backwards compatibility. Callers omitting it will not update concurrency state. Counter drifts upward over time.

**Mitigation:** All production agents should pass `agent_id`. The field is documented and encouraged. For recovery: same manual Redis reset as RISK 1.

### RISK 3 — INCR + EXPIRE Rate Limit Not Atomic (LOW)
Two concurrent first calls both `INCR` to 1, then both call `EXPIRE 120`. The second `EXPIRE` resets the TTL — idempotent and correct. No corrupted state.

### RISK 4 — Float Drift in INCRBYFLOAT (LOW)
Redis `INCRBYFLOAT` uses double-precision. At $0.50/task and 1,000 tasks/day, cumulative drift is sub-cent. No practical impact on 90%/100% threshold checks.

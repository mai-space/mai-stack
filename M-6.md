# M6 — Autonomous Execution

> Close the loop the system has been missing since M1: today, agents are pulled by a human who starts a local CLI tool and points it at the dispatcher. After M6, the dispatcher spins up its own agents. Each claimed task gets an isolated git worktree, an isolated ddev environment when the project needs one, a headless coding-agent process wired to the MCP servers automatically, a PHPStan/Rector/Playwright/Cypress quality gate before it's allowed to finish, and a durable, live-tailable journal of everything that happened. The whole stack runs unattended on a root server, restarts on boot, and backs itself up.

---

## Why This Milestone

M1–M5 built a governed task queue and a context-assembly brain, but the actual "agent" has always been a human-launched process on a laptop (`type: cursor`, `type: opencode`, `type: junie` in `agents.yml`, all pull-only, all external). Nothing in the stack today:

- creates a workspace for an agent to work in — agents share the developer's live checkout
- starts an agent process — a human runs `cursor` / `claude` / `opencode` manually
- verifies the agent's work — `complete_task` is called by the agent itself, on its own word
- records *what happened* durably — Redis pub/sub is transient; there is no execution history once a task is done
- knows about PHP tooling (ddev, PHPStan, Rector) or e2e tooling (Playwright, Cypress) at all
- can run unattended on a server without a person present to launch tools

M6 is the milestone that turns mai-stack from "a queue agents can pull from" into "a system that develops your projects while you're not looking."

Two new capability classes on top of the existing `type` field for agents:

- **`mode: external`** (default, unchanged) — today's behavior. A human runs a local tool that connects to the dispatcher and pulls tasks.
- **`mode: managed`** *(new)* — mai-runner starts, supervises, and tears down this agent itself. No human involved.

External and managed agents can coexist. A team can keep using Cursor by hand for exploratory work while managed agents grind through the backlog.

## mai-runner — the execution engine

The core new service. One supervisor loop per `mode: managed` agent profile. Each loop:

```
while true:
  if concurrency exhausted (global cap, agent cap, or per-project cap) → sleep(POLL_INTERVAL_MS); continue
  task ← claim_task(project_id, agent_id) via mai-dispatcher MCP gateway   // same call external tools make
  if no task → sleep(POLL_INTERVAL_MS); continue
  spawn runTask(task) as a detached worker; loop continues immediately (agents run in parallel up to their cap)
```

Managed agents claim through the **same** `claim_task` tool as external tools — governance, budget, affinity, and the freshness check from M2/M3 all apply unmodified. mai-runner is just another MCP client, distinguished only by who launched it.

### 1. Agent Adapters — the 9 supported backends

Not every managed agent is a spawned CLI process — some are raw model APIs with no CLI at all. mai-runner unifies both behind one interface instead of hard-coding a single invocation shape:

```typescript
interface AgentAdapter {
  family: 'cli' | 'api';
  prepare(worktree: Worktree, profile: AgentProfile, session: Session): Promise<void>;
  // cli family:  write the tool's own MCP config format into/near the worktree
  //              (.mcp.json, config.toml, etc.) so the subprocess auto-discovers mai-dispatcher.
  // api family:  no file — the runner opens its own in-process MCP client against the
  //              dispatcher's session-scoped SSE endpoint and bridges tool calls itself.
  invoke(worktree: Worktree, manifest: string, taskId: string): Promise<{ exitCode: number }>;
}
```

Adapters live in `mai-runner/src/adapters/`, one file per `type`, registered by name in a lookup table. Switching a profile's backend is a one-line `type:` change in `agents.yml` — the claim loop, gate pipeline, and journal are adapter-agnostic.

| `type` | Family | MCP wiring | Auth | Notes |
|---|---|---|---|---|
| `claude-cli` | cli | `.mcp.json` in worktree, `--mcp-config` flag | `ANTHROPIC_API_KEY` or CLI login | Reference implementation — build and validate first, every other adapter follows its shape |
| `codex-cli` | cli | per-task `CODEX_HOME` pointing at a generated `config.toml` with `[mcp_servers.mai]` | `OPENAI_API_KEY` or CLI login | `codex exec "<prompt>"` for non-interactive runs |
| `cursor-agent` | cli | project-level `.cursor/mcp.json` written into the worktree | Cursor CLI login/token | Non-interactive/print mode |
| `opencode-agent` | cli | `opencode.json` `mcp` block written into the worktree | provider key per `model_provider` | `opencode run "<prompt>"` |
| `antigravity-cli` | cli | **unverified** — confirm the tool's actual MCP config format before wiring it in | Google account / API key | **Spike required.** Newest and least-documented of the nine — do not add to production `agents.yml` until someone has hand-run one real task through it |
| `anthropic-api` | api | in-process MCP client, no file | `ANTHROPIC_API_KEY` | mai-runner drives its own tool-use loop (manifest → Claude Messages API → MCP tool calls), no subprocess. Build on the Anthropic SDK's Tool Runner rather than a hand-rolled loop |
| `openai-api` | api | in-process MCP client, no file | `OPENAI_API_KEY` | Same loop shape as `anthropic-api`, against OpenAI's function-calling API |
| `opencode-go-api` | api | in-process MCP client | opencode server auth token | Drives opencode's own persistent HTTP server mode (`opencode serve`) instead of spawning a fresh CLI process per task — one long-lived server, one session per worktree |
| `opencode-zen-api` | api | in-process MCP client | `OPENCODE_ZEN_API_KEY` | opencode's hosted model gateway. Same `api` adapter shape as `anthropic-api`/`openai-api`, just pointed at Zen's endpoint via `base_url` — confirm the exact endpoint/protocol during implementation |

`cli`-family profiles keep the `cli:` block already shown (`command`/`args`/`timeout_minutes`). `api`-family profiles use an `api:` block instead — no subprocess, so `timeout_minutes` becomes a wall-clock guard around the whole tool-use loop rather than a process timeout:

```yaml
  - id: managed-anthropic-direct
    type: anthropic-api
    mode: managed
    api:
      base_url: https://api.anthropic.com
      api_key_env: ANTHROPIC_API_KEY
      model: claude-sonnet-5
      timeout_minutes: 30
    task_types: [code, tests]
    max_parallel_worktrees: 2
    max_gate_retries: 3

  - id: managed-opencode-zen
    type: opencode-zen-api
    mode: managed
    api:
      base_url: https://api.opencode.ai/zen   # placeholder — confirm exact endpoint before shipping
      api_key_env: OPENCODE_ZEN_API_KEY
      model: <model-slug>
      timeout_minutes: 30
    task_types: [boilerplate, docs]
    max_parallel_worktrees: 2
```

`max_gate_retries` moves to the top level of the agent profile (out of `cli:`) since both families use it identically.

### 2. WorktreeManager (`worktree.ts`)

```typescript
async function createWorktree(project: Project, task: Task): Promise<Worktree> {
  const base = project.workspace;
  const branch = `agent/${task.id}-${slugify(task.title)}`;
  const path = `${base}/.worktrees/task-${task.id}`;

  await exec(`git -C ${base} fetch origin ${project.repo.base_branch}`);
  await exec(`git -C ${base} worktree add ${path} -b ${branch} origin/${project.repo.base_branch}`);
  return { path, branch, taskId: task.id };
}

async function destroyWorktree(project: Project, wt: Worktree, opts: { keep: boolean }): Promise<void> {
  if (opts.keep) return; // e.g. task ended in BLOCKED — leave it for the next attempt or a human
  await exec(`git -C ${project.workspace} worktree remove ${wt.path} --force`);
  await exec(`git -C ${project.workspace} branch -D ${wt.branch}`).catch(() => {}); // no-op if pushed/merged
}
```

Concurrency is enforced with a Redis semaphore, checked **before** `claim_task` so a project never over-commits:

```
runner:{project_id}:worktrees   (INCR on create, DECR on destroy, capped at min(agent.max_parallel_worktrees, project.runtime.max_parallel_worktrees, RUNNER_MAX_GLOBAL_WORKTREES))
```

`RUNNER_MAX_GLOBAL_WORKTREES` is a hard ceiling set once for the whole server — this is what actually protects the root server's RAM/CPU, since every worktree can spin up a full ddev stack (PHP-FPM, nginx, MySQL).

### 3. ddev lifecycle (`ddev.ts`)

Skipped entirely when `project.runtime.type !== 'ddev'`.

```typescript
async function ddevUp(worktree: Worktree, taskId: string): Promise<void> {
  const projectName = `t-${taskId.slice(0, 8)}`;
  // Each worktree is a separate directory, so ddev treats it as a separate project.
  // ddev's Traefik-based router (v1.22+) namespaces every project under its own
  // <name>.ddev.site hostname — unique project names are sufficient for safe
  // concurrent execution, no manual port bookkeeping required.
  await exec(`ddev config --project-name=${projectName} --project-type=php --docroot=public --update-config`, { cwd: worktree.path });
  await exec(`ddev start`, { cwd: worktree.path });
}

async function ddevExec(worktree: Worktree, command: string): Promise<GateResult> {
  return execCapture(`ddev exec ${command}`, { cwd: worktree.path });
}

async function ddevDown(worktree: Worktree): Promise<void> {
  await exec(`ddev delete -O -y`, { cwd: worktree.path }).catch(() => {}); // -O: omit snapshot, tear down fully
}
```

### 4. Adapter invocation (`invoke.ts` + `adapters/*.ts`)

`sessionToken` (used by every adapter below) comes from the dispatcher's new `POST /agents/:id/session` (see **Dispatcher auth**, below) — issued once per worktree, scoped to that task, revoked on completion.

**`cli` family** — reference implementation, `adapters/claude-cli.ts`. Writes the tool's MCP config into the worktree, spawns the subprocess, streams output to the journal line by line:

```typescript
export const claudeCli: AgentAdapter = {
  family: 'cli',

  async prepare(worktree, profile, session) {
    const config = {
      mcpServers: {
        'mai-dispatcher': {
          type: 'sse',
          url: `${process.env.DISPATCHER_URL}/sse`,
          headers: { 'X-Agent-Id': profile.id, 'X-Session-Token': session.token },
        },
      },
    };
    await writeFile(`${worktree.path}/.mcp.json`, JSON.stringify(config, null, 2));
  },

  async invoke(worktree, manifest, taskId) {
    const args = profile.cli.args.map(a => a.replace('{worktree}', worktree.path));
    const child = spawn(profile.cli.command, [...args, manifest], {
      cwd: worktree.path,
      timeout: profile.cli.timeout_minutes * 60_000,
    });

    child.stdout.on('data', c => journal.append(taskId, 'agent_output', { stream: 'stdout', text: c.toString() }));
    child.stderr.on('data', c => journal.append(taskId, 'agent_output', { stream: 'stderr', text: c.toString() }));

    return new Promise(resolve => child.on('close', code => {
      journal.append(taskId, 'agent_finished', { exit_code: code });
      resolve({ exitCode: code ?? -1 });
    }));
  },
};
```

`codex-cli`, `cursor-agent`, and `opencode-agent` follow the identical shape — only `prepare()`'s config format and `invoke()`'s command/args differ (see the adapter table above for each tool's config file and non-interactive invocation flag).

**`api` family** — no subprocess, `adapters/anthropic-api.ts`. mai-runner hosts its own in-process MCP client against the dispatcher's session-scoped SSE endpoint and drives a tool-use loop directly against the model API:

```typescript
export const anthropicApi: AgentAdapter = {
  family: 'api',

  async prepare(worktree, profile, session) {
    // no file to write — the in-process MCP client authenticates with the same
    // X-Agent-Id / X-Session-Token headers a CLI adapter would put in .mcp.json
    this.mcpClient = await connectMcpClient(`${process.env.DISPATCHER_URL}/sse`, {
      'X-Agent-Id': profile.id, 'X-Session-Token': session.token,
    });
  },

  async invoke(worktree, manifest, taskId) {
    // Built on the Anthropic SDK's Tool Runner: registers this.mcpClient's tools,
    // loops Messages API calls until the model stops requesting tool use or errors out.
    const runner = anthropic.beta.messages.toolRunner({
      model: profile.api.model,
      system: 'You are a coding agent working inside a git worktree. Use the available MCP tools.',
      messages: [{ role: 'user', content: manifest }],
      tools: await this.mcpClient.listTools(),
      max_tokens: 8192,
    });

    for await (const event of runner) {
      journal.append(taskId, 'agent_output', { stream: 'model', event });
      if (event.type === 'tool_use') {
        const result = await this.mcpClient.callTool(event.name, event.input); // executes in worktree.path
        runner.submitToolResult(event.id, result);
      }
    }

    journal.append(taskId, 'agent_finished', { exit_code: 0 });
    return { exitCode: 0 };
  },
};
```

`openai-api`, `opencode-go-api`, and `opencode-zen-api` reuse this shape with a different SDK/endpoint behind `this.mcpClient`/the model call — the loop, journal calls, and worktree scoping stay identical. `opencode-go-api` additionally reuses one persistent `opencode serve` process across tasks (started once per profile, not per task) instead of opening a fresh connection each time.

### 5. Quality gate pipeline (`gates.ts`)

Runs after every agent invocation, before `complete_task` is ever called:

```typescript
async function runQualityGates(project: Project, worktree: Worktree, taskId: string): Promise<GateResult[]> {
  const results: GateResult[] = [];
  const exec = project.runtime.type === 'ddev' ? ddevExec : localExec;

  if (project.quality_gates?.phpstan?.enabled) {
    const r = await exec(worktree, project.quality_gates.phpstan.command);
    await journal.append(taskId, 'gate_result', { gate: 'phpstan', pass: r.exitCode === 0, output: r.stdout.slice(0, 4000) });
    results.push({ gate: 'phpstan', ...r });
  }

  if (project.quality_gates?.rector?.enabled) {
    const cfg = project.quality_gates.rector;
    const r = await exec(worktree, cfg.command);
    if (cfg.mode === 'apply' && r.exitCode !== 0) {
      // dry-run found changes to apply — apply them, then let phpstan/e2e re-validate
      await exec(worktree, cfg.command.replace('--dry-run', ''));
    }
    await journal.append(taskId, 'gate_result', { gate: 'rector', pass: cfg.mode === 'apply' || r.exitCode === 0, output: r.stdout.slice(0, 4000) });
    results.push({ gate: 'rector', ...r });
  }

  if (project.quality_gates?.e2e?.enabled) {
    const r = await exec(worktree, project.quality_gates.e2e.command);
    await journal.append(taskId, 'gate_result', { gate: project.quality_gates.e2e.tool, pass: r.exitCode === 0, output: r.stdout.slice(0, 4000) });
    results.push({ gate: project.quality_gates.e2e.tool, ...r });
  }

  return results;
}
```

### 6. The full task loop (`loop.ts`)

```typescript
async function runTask(profile: AgentProfile, project: Project, task: Task, manifest: string): Promise<void> {
  const adapter = getAdapter(profile.type);   // one lookup, everything below is adapter-agnostic
  const worktree = await createWorktree(project, task);
  await journal.append(task.id, 'agent_started', { agent_id: profile.id, worktree: worktree.path, branch: worktree.branch, adapter: profile.type });

  if (project.runtime.type === 'ddev') await ddevUp(worktree, task.id);
  const session = await dispatcherClient.issueSession(profile.id, task.id);
  await adapter.prepare(worktree, profile, session);

  let gatesPassed = false;
  for (let attempt = 1; attempt <= (profile.max_gate_retries ?? 1); attempt++) {
    const { exitCode } = await adapter.invoke(worktree, manifest, task.id);
    if (exitCode !== 0) continue; // agent process/loop errored — retry or fall through to blocker below

    const gates = await runQualityGates(project, worktree, task.id);
    gatesPassed = gates.every(g => g.pass);
    if (gatesPassed) break;

    manifest += `\n\n═══ GATE FAILURES (attempt ${attempt}) ═══\n` +
      gates.filter(g => !g.pass).map(g => `${g.gate}:\n${g.output}`).join('\n\n') +
      `\nFix the above and try again.`;
  }

  if (project.runtime.type === 'ddev') await ddevDown(worktree);

  if (!gatesPassed) {
    // Agent already had every opportunity to call flag_risk/create_subtask itself.
    // If it didn't and gates still fail after all retries, the runner escalates on its behalf.
    await dispatcherClient.flagRisk(task.id, `Quality gates failed after ${profile.cli.max_gate_retries} attempt(s)`, 'medium');
    await destroyWorktree(project, worktree, { keep: true }); // leave it for inspection
    return;
  }

  await commitPushAndOpenPr(project, worktree, task);
  await dispatcherClient.completeTask(task.id, profile.id);
  await destroyWorktree(project, worktree, { keep: false });
  await journal.append(task.id, 'run_complete', { branch: worktree.branch });
}
```

If the agent itself calls `request_decision`, `request_clarification`, or `flag_risk` mid-run (the existing M1 blocker tools — unchanged), the task moves to `BLOCKED` and the *next* poll simply won't re-claim it. The current worktree is kept (`{ keep: true }`) so a resumed run — after human response — reuses the same branch instead of starting over.

### 7. Commit / push / PR strategy (`git.ts`)

```typescript
async function commitPushAndOpenPr(project: Project, worktree: Worktree, task: Task): Promise<void> {
  await exec(`git -C ${worktree.path} add -A`);
  await exec(`git -C ${worktree.path} commit -m ${shellQuote(`${task.title}\n\n${task.description ?? ''}\n\nTask: #${task.id}`)}`);
  await exec(`git -C ${worktree.path} push -u origin ${worktree.branch}`);

  if (project.pr_strategy === 'push-branch-only') return;

  const pr = await openPullRequest(project.repo, worktree.branch, project.repo.base_branch, task);
  if (project.pr_strategy === 'auto-merge') {
    await mergePullRequest(project.repo, pr.number); // only reached if quality gates already passed and no RISK was flagged this run
  }
}
```

## mai-journal — durable execution history

Redis pub/sub (used everywhere else in the stack) is fine for live UI updates but has no memory — restart Redis and the history of what an agent did is gone. mai-journal is the first durable, queryable record of agent *execution*, distinct from mai-memory-mcp's durable record of agent *decisions*.

### Schema

```typescript
interface JournalEntry {
  id: string;
  task_id: string;
  project_id: string;
  agent_id: string;
  kind: 'agent_started' | 'agent_output' | 'gate_result' | 'agent_finished' | 'run_complete' | 'error' | 'note';
  payload: string;   // JSON
  created_at: string;
}
```

SQLite-backed (same pattern as mai-project-mcp / mai-registry), one file, no external dependency.

### REST API

```
POST /journal/:taskId/entries        { agent_id, kind, payload }   ← used by mai-runner
GET  /journal/:taskId/entries?since=<id>                            ← dashboard tail / initial load
GET  /projects/:id/journal?limit=50                                  ← recent activity across a project
```

Every write also publishes to `journal.{task_id}` on Redis — the dashboard's existing WebSocket relay (`ws.ts`, unchanged since M4) picks this up exactly like it already does for `task.*` channels, so **no new transport is needed**, only a new channel prefix to subscribe to.

### New MCP tool: `journal_note`

Exposed through the dispatcher gateway (`mai-dispatcher/src/mcp/tools/journal-tools.ts`, same proxy pattern as `memory-tools.ts`) so an agent — managed or external — can write a freeform note into the journal without mai-runner's involvement:

```
journal_note(task_id, message)
```

Useful for external/human-launched agents too: it gives every task a running commentary even outside the managed pipeline.

## Dispatcher: session auth (required before exposure)

Today `mai-dispatcher`'s MCP endpoint has **no authentication** — acceptable when it's only reachable from `localhost` on a developer's laptop, not acceptable once it's proxied to the public internet for a root-server deployment. M6 adds short-lived, per-worktree session tokens:

```
POST /agents/:agentId/session   → { session_token, expires_at }   (issued by mai-runner per task, or by an operator for external tools)
```

Every SSE connection and `tools/call` on the dispatcher now requires `X-Agent-Id` + `X-Session-Token` headers, verified against Redis (`session:{token} → agentId`, TTL matching the task lease). External tools get a long-lived token issued once via the dashboard (Settings page, out of scope for the code in this milestone — token issuance API only). This closes the one real hole in exposing the dispatcher publicly.

## Production Deployment

### Reverse proxy + TLS (`Caddyfile`)

```
dashboard.example.com {
  reverse_proxy mai-dashboard:3461
}

mcp.example.com {
  reverse_proxy mai-dispatcher:3460
}
```

Caddy handles Let's Encrypt automatically — no cert management. Only `mai-dashboard` and `mai-dispatcher` are ever reachable from outside; every other service stays on the internal `mai` Docker network, same as today.

### `docker-compose.prod.yml` (override)

- Drops all `ports:` host bindings except Caddy's 80/443.
- Adds `mem_limit` / `cpus` per service — critical for `mai-runner`, since each concurrent ddev stack is effectively its own PHP+MySQL server.
- `restart: always` everywhere.

### systemd unit (`deploy/mai-stack.service`)

```ini
[Unit]
Description=mai-stack
Requires=docker.service
After=docker.service

[Service]
WorkingDirectory=/opt/mai-stack
ExecStart=/usr/bin/docker compose -f docker-compose.yml -f docker-compose.prod.yml up
ExecStop=/usr/bin/docker compose -f docker-compose.yml -f docker-compose.prod.yml down
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Boots the whole stack automatically on server restart.

### Backups (`deploy/backup.sh`, nightly cron)

`.backup` dump of every SQLite file (registry, project-mcp, mai-journal) + `redis-cli --rdb` snapshot, tarred and pushed off-box (rsync/rclone target configurable). 7 daily + 4 weekly retention.

## Risks

### RISK 1 — ddev requires the Docker socket (HIGH)
`ddev` shells out to Docker to manage its per-project containers. Giving `mai-runner`'s container the host Docker socket is equivalent to granting it host root. Two mitigations, pick one before production:
- Run `mai-runner` directly on the host (outside Docker Compose), with Docker CLI installed natively — the agent CLI and ddev then behave exactly as they would on a developer's machine, at the cost of losing container isolation for the runner process itself.
- Front the socket with a restricting proxy (e.g. `tecnativa/docker-socket-proxy`) that only allows the container/exec/network operations ddev actually needs, denying volume/image/system-level calls.
Do not mount `/var/run/docker.sock` unproxied into a container that also executes arbitrary agent-written shell commands.

### RISK 2 — an unattended coding agent has real shell and filesystem access (HIGH)
Worktree isolation (RISK-contained to one directory) and the existing budget/rate-limit governance (M3) bound cost and blast radius, but a managed agent can still run arbitrary commands inside its worktree and, via ddev, inside its own containers. Always run the CLI with the most restrictive permission mode the tool offers (`--permission-mode acceptEdits`, never a mode that allows unprompted destructive host commands), and never grant the agent's `.mcp.json` any server beyond mai-dispatcher's scoped gateway.

### RISK 3 — root-server resource exhaustion (MEDIUM)
Every concurrent ddev-backed worktree is a full PHP-FPM + MySQL stack. `RUNNER_MAX_GLOBAL_WORKTREES` is the single knob that prevents an OOM cascade; size it to the box (rule of thumb: reserve ~2GB per concurrent ddev stack, plus the baseline stack). Start conservative (1–2) and raise only after watching real memory usage.

### RISK 4 — Rector `apply` mode can introduce silent unwanted refactors (MEDIUM)
Default every project to `mode: dry-run` (must be clean to pass the gate, never mutates code on its own). `apply` mode is an explicit per-project opt-in and is always re-validated by PHPStan/e2e in the same gate pass before the task can complete.

### RISK 5 — branch/worktree sprawl (LOW)
Every managed run creates a branch; only successful runs get torn down automatically. Add a periodic prune job (not in this milestone's build order, but budget for it in M7) that deletes merged branches and worktrees older than a configurable age.

### RISK 6 — exposing the dispatcher publicly without RISK 1's fix in place (MEDIUM)
Session-token auth (this milestone) stops an unauthenticated caller from claiming tasks or reading manifests, but does not by itself stop a compromised managed-agent session from doing damage inside its own worktree — see Risk 2. Auth and sandboxing are separate controls; ship both.

### RISK 7 — nine backends means nine different failure modes (MEDIUM)
Each `cli`-family tool has its own MCP config format, its own non-interactive/print flag, its own idea of "done" (exit code semantics vary), and its own auth/login flow — some of which (`cursor-agent`, `opencode-agent`) may require an interactive login step the first time, which does not work unattended on a server. Each `api`-family backend has its own SDK, tool-calling wire format, and error/retry behavior. Budget the codex-cli, cursor-agent, and opencode-agent adapters as small individual spikes, not one afternoon of "same as claude-cli." `antigravity-cli` specifically has no confirmed MCP config format as of this plan — treat it as research, not implementation, until that's verified against the real tool.

## Implementation Notes (post-build)

A handful of places the shipped code diverges from this plan's illustrative snippets, worth recording for anyone reading the two side by side:

- **Credentials travel as `?agent_id=&token=` query params on the SSE URL**, not custom headers. This works identically across every MCP SDK version and every cli tool's own MCP transport, where custom-header support on the initial SSE connection isn't guaranteed — see `mai-runner/src/mcpBridge.ts`.
- **`anthropic-api` and `openai-api` drive a hand-rolled Messages/Chat-Completions tool-use loop**, not the SDK's `toolRunner` helper referenced in the original sketch — the manual loop's shape is unambiguous and was verified to compile against the real installed SDKs; the helper's exact iteration API wasn't.
- **mai-runner reads `config/projects.yml` directly** (mounted read-only, same file mai-registry seeds from) rather than through mai-registry's REST API, since `runtime`/`quality_gates`/`repo`/`pr_strategy` are M6-only fields mai-registry's DB schema and migrations don't carry. This avoided a schema migration on an already-stable service; mai-registry is untouched by M6.
- **Docker-socket / ddev wiring is not enabled anywhere by default** — not in `docker-compose.yml`, and only as commented-out blocks in `docker-compose.prod.yml`. Operators enabling `runtime.type: ddev` must read RISK 1 and wire the socket-proxy themselves.
- **`antigravity-cli` has no adapter file** — per this plan's own guidance, it stays a spike, not shipped code.
- One pre-existing, unrelated type bug was fixed in passing while verifying the build: `mai-dispatcher/src/mcp/tools/task-tools.ts`'s local `Task` interface was missing `blocker_type`/`blocker_payload`/`blocker_resolved_at`, which `assembleManifest()` requires — the fields were always present on the actual API response, just untyped.

All new and touched TypeScript (mai-journal, mai-runner, mai-dispatcher, mai-dashboard server + frontend) was verified with `tsc --noEmit` / `vite build` against real installed dependencies before commit.

## What M6 Does Not Include

- Multi-tenant dashboard auth (still one shared `DASHBOARD_SECRET`, per M5)
- Automatic branch/worktree pruning for abandoned runs (flagged for M7)
- Non-ddev PHP orchestration (Lando, Docksal, plain Docker Compose per-project) — ddev only
- Auto-merge as a default (`pr_strategy` defaults to `open-pr`; `auto-merge` is explicit opt-in)
- A production-ready `antigravity-cli` adapter — its MCP config format needs verification before it ships; the other eight backends are in scope for this milestone
- A generic git-provider abstraction beyond GitHub for `openPullRequest`/`mergePullRequest`
- Cost-based model routing beyond the existing per-agent budget system
- Windows-hosted mai-runner (Docker socket / ddev assumptions are Linux-first, matching the root-server target)
